# الطبقة ٣ — الأنظمة الفرعية للنواة (خدمات فضاء المستخدم)

> **الطبقة:** ٣ - الأنظمة الفرعية للنواة (خدمات فضاء المستخدم)
> **الحالة:** وثيقة معمارية
> **لغة التنفيذ:** Rust لكل شيء، إلا حيث يُذكر استثناء صراحةً
> **نوع التشغيل:** فضاء المستخدم، لكن بأولوية جدولة عالية (near-kernel priority)، كل خدمة عملية منفصلة ومعزولة بـ Capability محدود

---

## 0. العلاقة بالطبقة السفلى والعليا

**الطبقة السفلى (النواة الصغرى، الطبقة ٢):** كل خدمة في هذه الطبقة (Device Manager، VFS، Netstack، Compositor، mm-service) هي عملية عادية في فضاء المستخدم تتحدث مع النواة الصغرى فقط عبر **استدعاء النظام (syscall) + Capability** (وهي بالضبط الحدود الموصوفة في وثيقة الطبقة ٢، القسم ٠). لا تملك هذه الخدمات أي امتياز خاص مقارنة بتطبيق عادي من الطبقة ٥؛ الفارق الوحيد هو أن Root Task منحتها المزيد من الـ Capabilities عند بدء التشغيل (مثل Capability للوصول إلى MMIO الخاص بجهاز معين).

**الطبقة العليا (خدمات النظام، الطبقة ٤):** يتم الاتصال عبر **بروتوكول IPC عالي المستوى** مُعرَّف بواسطة IDL مشترك (القسم ٣ من هذه الوثيقة) — وليس عبر استدعاءات نظام خام. أمثلة:
- عندما تُستدعى `open()` في POSIX Compat Layer (الطبقة ٤)، تُرسل هذه الطبقة داخلياً طلب `FsRequest::Open` إلى VFS Service
- يُجري Package Manager (الطبقة ٤) اتصال IPC مع VFS Service و Device Manager (لأجل مساحة القرص/الجهاز الهدف) لتثبيت حزمة ما
- يقوم Security Broker (الطبقة ٤) بالتحقق من صحة الـ Capabilities التي يصدرها هو نفسه (مثل الوصول إلى برنامج تشغيل معيّن) ونقلها في النهاية عبر النواة الصغرى (الطبقة ٢)، لكن القرار السياسي «من يملك الإذن» يُتخذ في الطبقة ٤

ملاحظة معمارية مهمة: **لا تقوم الطبقة ٤ أبداً باستدعاء النواة الصغرى (الطبقة ٢) مباشرة** إلا لعمليات إدارية محدودة جداً (مثل إصدار Capability، وهو ما يتطلب بحد ذاته وصولاً على مستوى النواة الصغرى)؛ مسار البيانات الرئيسي يمر دائماً عبر بروتوكولات هذه الطبقة (٣).

تحتوي هذه الطبقة على كل ما «يظن الجميع أنه جزء من النواة»، لكن في الواقع لا شيء منه ذو امتياز (Privileged). كل مكوّن في هذه الطبقة هو عملية منفصلة على مستوى النواة الصغرى، ولا يملك وصولاً إلا إلى الـ Capabilities الممنوحة له صراحةً.

**تُسمّى أول عملية تُشغّلها النواة الصغرى بـ «Root Task»**، وهي المسؤولة عن الإقلاع الأولي لهذه الأنظمة الفرعية وتوزيع الـ Capabilities الأولية (بما في ذلك حصة كل خدمة من UntypedMemory).

## 2. المكونات الرئيسية

### 2.1 Device Manager (مدير برامج التشغيل)

```
device-manager/
 ├── يستقبل Hardware Manifest (عبر IPC مع Root Task التي حصلت عليه من HAL)
 ├── يُشغّل عملية منفصلة لكل برنامج تشغيل (Driver Process Isolation)
 ├── يُصدر Capability محدوداً لكل برنامج تشغيل:
 │    - فقط منطقة MMIO الخاصة بذلك الجهاز (وليس الذاكرة كلها)
 │    - فقط IRQ الخاص بذلك الجهاز
 └── سياسة إعادة التشغيل: عند انهيار برنامج تشغيل ← يُعيد Device Manager تشغيله
     في عملية جديدة دون أن ينام النظام بأكمله (وهذا أهم إنجاز لهذه الهندسة المعمارية بأكملها مقارنة بنواة لينكس الأحادية الكتلة)
```

**نموذج كتابة برامج التشغيل:**
```rust
#[async_trait]
pub trait DeviceDriver {
    fn probe(manifest_entry: &ComputeDevice) -> Result<Self, DriverError> where Self: Sized;
    async fn handle_irq(&mut self, irq: IrqId);
    async fn handle_request(&mut self, req: DriverRequest) -> DriverResponse;
}
```
كل برنامج تشغيل هو صندوق (crate) منفصل بلغة Rust ينفّذ هذا الـ trait، ويُجمَّع (compile) ويُشغَّل داخل صندوق رملي (sandbox) خاص بعملية مستقلة.

### 2.2 VFS Service (نظام الملفات)

- بدلاً من أن يكون نظام الملفات جزءاً من النواة (كما في لينكس)، يكون كل نظام ملفات (ext4-compat، btrfs-compat، نظام ملفات أصلي جديد) **خدمة منفصلة** تقع خلف VFS Router
- يتم الاتصال بين التطبيق و VFS عبر IPC (الطبقة ٢) باستخدام بروتوكول رسائل موحّد (`FsRequest`/`FsResponse`)
- من أجل الأداء: تُنفَّذ ذاكرة التخزين المؤقت للصفحات (page cache) على شكل Shared Memory Region بين VFS Service وKernel Memory Manager لتجنب النسخ الإضافي

```rust
pub enum FsRequest {
    Open { path: PathBuf, flags: OpenFlags },
    Read { handle: FileHandle, offset: u64, len: usize },
    Write { handle: FileHandle, offset: u64, shared_buf: Capability },
    Stat { path: PathBuf },
    // ...
}
```

- **نظام الملفات الأصلي المقترح لهذا المشروع:** تصميم جديد يدعم copy-on-write وحساب المجاميع الاختبارية (checksumming) (على غرار فلسفة ZFS/btrfs)، مكتوب بالكامل بلغة Rust (يمكن البدء بالاستلهام من صناديق موجودة مثل مشروع RedoxFS التابع لـ Redox، لكن بالنسبة للـ MVP يجب تعريف endianness وتنسيق القرص (on-disk format) من الصفر وتوثيقهما)

### 2.3 Network Stack (كومة الشبكة)

- تنفيذ كامل لـ TCP/IP في فضاء المستخدم (على غرار Netstack الخاص بـ Fuchsia أو مشروع smoltcp في منظومة Rust)
- يتم الاتصال بكرت الشبكة عبر Device Manager + Capability محدود بذلك الجهاز
- **القرار: دعم kernel-bypass على طراز DPDK منذ الـ MVP نفسه** (وليس المرحلة الثانية) — لأن كلاً من ملف تعريف الذكاء الاصطناعي (شبكة موزّعة منخفضة التأخر بين عقد الاستدلال) وملف تعريف الألعاب (شبكة اتصال عبر الإنترنت منخفضة التأخر) يعتمدان على ذلك، وإضافته لاحقاً تعني عادةً إعادة تصميم الواجهة البرمجية (API). الآلية: يقوم تطبيق يملك Capability خاصاً بتعيين (map) مخزن NIC مباشرة (عبر `hal-direct`، الطبقة ١) وإرسال البيانات دون المرور بمسار IPC/Netstack المعتاد.

```rust
pub trait KernelBypassNetworking {
    fn request_direct_nic_access(&self, token: CapabilityToken, nic: DeviceId)
        -> Result<DirectNicHandle, NetstackError>;
    fn poll_rx_ring(&self, handle: DirectNicHandle) -> &[RawPacket];
    fn submit_tx_ring(&self, handle: DirectNicHandle, packets: &[RawPacket]);
}
```

هذا المسار موازٍ تماماً ومستقل عن مسار Netstack المعتاد (أعلاه)؛ تستمر التطبيقات العامة في استخدام المسار القياسي (بما فيه من عبء IPC المعتاد، لكن مع أمان وعزل كاملَين)، ولا يصل إلى هذا المسار إلا التطبيقات التي تملك Capability صريحاً من Security Broker (الطبقة ٤).

### 2.4 Compositor Service — مكانة واجهة المستخدم في الهندسة المعمارية

هذا هو الجواب عن السؤال الجوهري «أين تقع واجهة المستخدم (UI) في الهندسة المعمارية؟». القرار: **خدمة Compositor واحدة في هذه الطبقة نفسها (بنية تحتية مشتركة)، مقابل مديري النوافذ (Window Managers)/بيئات سطح المكتب (DEs) التي تقع في الطبقة ٥ كتطبيقات أصلية يختارها المستخدم بحرية.**

```
┌─────────────────────────────────────────┐
│ الطبقة ٥: بيئات سطح المكتب/مديرو النوافذ    │  ← المستخدم يختار بحرية
│  (شبيهة بـ GNOME، شبيهة بـ KDE، WM بلاطي،  │
│          أو لا شيء بالنسبة لخادم)          │
├─────────────────────────────────────────┤
│ الطبقة ٣: Compositor Service (هذا القسم)   │  ← بنية تحتية مشتركة، ثابتة دائماً
└─────────────────────────────────────────┘
```

**قرار البروتوكول:** بروتوكول أصلي وجديد بالكامل (غير متوافق مع Wayland)، لأن الهدف الأساسي للهندسة المعمارية هو نقل نموذج Capability إلى أعلى طبقة من واجهة المستخدم. لو بُني الأمر فوق Wayland، فإن نموذج الأذونات (permission) القديم الخاص به سيتسرب حتماً إلى ما تحت البروتوكول الجديد. إذا احتاج الأمر لاحقاً إلى دعم برمجيات لينكس من نوع GTK/Qt، فسيتم ذلك عبر **Linux Compat Runtime (الطبقة ٥)**، وليس بتلويث هذه الخدمة البنيوية ببروتوكول خارجي.

```rust
pub trait DisplayProtocol {
    fn create_surface(&self, client: ProcessId) -> Result<SurfaceHandle, CompositorError>;
    fn commit_buffer(&self, surface: SurfaceHandle, buf: Capability); // zero-copy، buf من ذاكرة GPU
    fn destroy_surface(&self, surface: SurfaceHandle);
    fn input_event_stream(&self, client: ProcessId) -> EventStream;   // غير متزامن، عبر Notification (الطبقة ٢)
    fn output_topology(&self) -> Vec<OutputInfo>;                      // شاشات متعددة، الدقة، معدل التحديث
}
```

**العلاقة بـ Compute Device Discovery (الطبقة ١):** يتحدث Compositor مباشرة مع Device Manager (القسم ٢.١ من هذه الوثيقة) للوصول إلى GPU، ويستخدم الذاكرة المشتركة zero-copy (الطبقة ٢، القسم ٥.٢) لنقل الإطارات (frames) بين التطبيق والشاشة — دون نسخ إضافي، خلافاً للنماذج الأقدم مثل X11.

**العلاقة بـ Profile Policy (الطبقة ٤):** هذه الخدمة عضو في `services_enabled_by_default`، لكنها **لا تُحمَّل افتراضياً في ملف تعريف الذكاء الاصطناعي (خادم headless)** — تماماً وفق نموذج Discovery+Policy: تظل HAL تكتشف GPU (للاستخدام الحسابي للذكاء الاصطناعي)، لكن خدمة عرض الصورة فقط لا حاجة لتحميلها.

### 2.5 Memory Manager Service (المستوى العالي)

ملاحظة: هذا يختلف عن «إدارة الذاكرة الخام» في النواة الصغرى (الطبقة ٢). هذه الخدمة هي صانعة السياسات:
- قرار swapping/paging (إن كان النظام يملك swap)
- سياسة OOM (أي عملية تُضحّى بها عند نقص الذاكرة) — قابلة للضبط بواسطة Profile Policy في الطبقة ٤
- إدارة Unified Memory لأجهزة الحوسبة (التنسيق بين تجمّع ذاكرة CPU/GPU/NPU، بناءً على قدرة CXL المُبلَّغ عنها في Hardware Manifest)

## 3. تعريف بروتوكول IPC — العقد بين الخدمات

لتجنب الالتباس في إدارة الإصدارات، تُعرَّف جميع الرسائل بين الخدمات في هذه الطبقة باستخدام **IDL مشترك** (اقتراح: تنسيق شبيه بـ Cap'n Proto، أو IDL مخصص خفيف الوزن بدلاً من protobuf، تجنباً لعبء التسلسل (serialization) على المسار عالي حركة المرور). يُنتج مخرج IDL كود Rust آمن الأنواع (type-safe) يُستخدم داخل `kernel-ipc` (الطبقة ٢).

```
 │    ├── driver-framework/    # trait المشترك DeviceDriver + sandbox runtime
 │    ├── driver-nvme/

 │    ├── driver-npu-generic/
 │    └── ...

 │    ├── vfs-router/
 │    ├── fs-native/           # نظام الملفات الأصلي الجديد
 │    └── fs-compat-ext4/      # قراءة/كتابة متوافقة فقط، لترحيل البيانات من لينكس
 ├── netstack/

```

## 5. معايير اكتمال الـ MVP
1. تنجح Root Task في تشغيل Device Manager، وVFS Service حدّي (minimal)، وبرنامج تشغيل كتلة بسيط (مثل virtio-blk على QEMU)
2. انهيار متعمّد لبرنامج تشغيل (panic مُحقَن في اختبار) ← يعيد Device Manager تشغيله دون أن يتأثر بقية النظام (يجب أن يكون هذا اختباراً آلياً في CI، وليس مجرد ادعاء)
3. تستطيع VFS Service تحميل (mount) نظام ملفات بسيط وتنفيذ عمليات قراءة/كتابة أساسية عبر IPC
4. تستطيع Netstack استقبال/إرسال حزمة ICMP echo (ping) على QEMU مع virtio-net
4.1. مسار kernel-bypass: يجب أن يتمكن تطبيق اختباري يملك Capability خاصاً من إرسال واستقبال حزم مباشرة على rx/tx ring لبطاقة شبكة افتراضية (virtio-net بدعم للـ bypass) دون المرور عبر Netstack؛ يجب أن يكون قياس (benchmark) زمن الاستجابة أقل بشكل ملحوظ (٣٠-٤٠٪ على الأقل) من المسار القياسي
4.2. Compositor Service: يجب أن يتمكن عميل اختباري من إنشاء surface، وتثبيت (commit) مخزن مؤقت (buffer)، وأن يُعرض ذلك المخزن المؤقت على الشاشة دون نسخ إضافي (zero-copy مُتحقَّق منه بأداة profiling) (حتى مخرجات headless/ملف كافية لغرض الـ MVP)
5. Benchmark: يجب الإبلاغ عن معدل نقل (throughput) القراءة/الكتابة لـ VFS مقارنةً بنظام مرجعي (حالياً لينكس على نفس إعداد QEMU) — يجب ألا ينخفض بأكثر من ٢٠-٣٠٪ في الـ MVP (بسبب عبء IPC)

## 6. القرارات المحسومة نهائياً
- **`fs-compat-ext4`:** أداة ترحيل بيانات لمرة واحدة من أنظمة لينكس، وليست جزءاً دائماً من الهندسة المعمارية. بعد استقرار نظام الملفات الأصلي، يمكن نقل هذه الوحدة إلى أداة سطر أوامر (CLI) مستقلة للترحيل (خارج نواة نظام التشغيل) حتى لا يبقى VFS Router يحمل هذا التعقيد بشكل دائم.
- **kernel-bypass على طراز DPDK:** منذ الـ MVP نفسه (وفقاً للقسم ٢.٣ أعلاه).
- **مكانة Compositor/واجهة المستخدم:** محسومة وفقاً للقسم ٢.٤ أعلاه.
