# الطبقة ٢ — النواة الصغرى (مبنية على Capability)

> **الطبقة:** ٢ - النواة الصغرى (مبنية على Capability)
> **الحالة:** وثيقة معمارية
> **لغة التنفيذ:** Rust (`no_std` حتى حدود IPC؛ لا يجوز لأي جزء من هذه الطبقة أن يعتمد على مخصص كومة (heap allocator) غير محدود أو على آلية panic-unwinding العادية)
> **نوع التشغيل:** فضاء النواة (Kernel-space)، الوضع المُمتاز (Privileged mode)
> **مصدر الإلهام التصميمي:** seL4 (نموذج الـ capability وإمكانية الإثبات)، Zircon (نموذج IPC ومقابض الكائنات object handle)

---

## 0. العلاقة بالطبقة السفلى والعليا

**الطبقة السفلى (HAL، الطبقة ١):** وفقاً لوثيقة الطبقة ١ (القسم ٠)، هذا الاتصال من جهة النواة الصغرى هو **استدعاء دالة/trait مباشر**، وليس IPC — يتم ربط كلتا الطبقتين في ملف ثنائي واحد ذي امتياز (Privileged). تُهيَّأ النواة الصغرى بواسطة `HardwareManifestRaw` (وثيقة الطبقة ١، القسم ٩) لحظة الإقلاع.

**الطبقة العليا (خدمات فضاء المستخدم، الطبقة ٣):** يتم الاتصال عبر **حدود استدعاء النظام (syscall)** — وهي النقطة الوحيدة في كامل الهندسة المعمارية التي يحدث فيها فعلياً تبديل سياق (context switch) على مستوى العتاد (من Ring 3/EL0/U-mode إلى Ring 0/EL1/M-mode):

```
عملية الطبقة ٣  --[syscall/svc/ecall instruction]-->  النواة الصغرى (الطبقة ٢)
عملية الطبقة ٣  <--[العودة بالنتيجة في السجل]---------  النواة الصغرى (الطبقة ٢)
```

طبقة استدعاءات النظام (القسم ٦، `SyscallOp`) هي الواجهة البرمجية الوحيدة التي تملكها الطبقة ٣ فما فوق للتحدث مع النواة الصغرى. حتى الـ IPC الفعلي بين عمليتين من الطبقة ٣ (مثلاً تطبيق مع VFS) يمر عبر نفس المسار: كلا الطرفين يتحدثان مع النواة الصغرى (`ipc_call`/`ipc_send_async`)، والنواة الصغرى هي الوسيط لنقل الرسائل/الـ Capability، وليس أن تصل العمليتان إلى بعضهما مباشرة. صندوق `kernel-ipc` (القسم ٧) يغلف هذه الحدود على شكل واجهة برمجية أعلى مستوى لـ Rust في الطبقة ٣ حتى لا يُضطر الكود الأعلى إلى كتابة تعليمات trap خام.

يجب أن تكون النواة الصغرى **أصغر قدر ممكن من الكود العامل في الوضع المُمتاز**. القاعدة الذهبية:

> إذا كان بالإمكان تنفيذ ميزة ما في فضاء المستخدم، فهي لا تنتمي إلى النواة.

لهذه الطبقة أربع مسؤوليات فقط لا أكثر: **إدارة الذاكرة، الجدولة (Scheduling)، الـ IPC، والـ Capability**. نظام الملفات، برامج التشغيل، الشبكة، وحتى مفهوم «العملية» بمعناه التقليدي — كلها موجودة في الطبقة ٣ (فضاء المستخدم).

## 1.1 القرار: يتم تصميم إمكانية الإثبات الصوري (Formal Verification) منذ اليوم الأول

الإثبات الصوري الكامل (على طريقة seL4) ليس ضمن نطاق الـ MVP نفسه، لكن **يُكتب الكود منذ البداية وفق قيود تُبقي مسار إمكانية الإثبات مفتوحاً في المرحلة الثانية**، بدلاً من الاضطرار لإعادة كتابته لاحقاً:

- يُمنع استخدام `unsafe` دون تعليق توضيحي موثق (وفقاً للقسم ٧ من وثيقة HAL؛ هذه القاعدة هنا أكثر إلزامية لأن هذه الطبقة ذات امتياز)
- يجب كتابة موزّع استدعاءات النظام (syscall dispatcher) على شكل **آلة حالات (state machine) صريحة**؛ يجب أن يكون لكل دالة أثر محدود وقابل للتتبع، دون أي أثر جانبي خفي أو تعديل عبر حالة عامة (global state) متناثرة
- بنية Capability Derivation Tree (القسم ٢) تتبع بدقة النمط المُثبت في seL4، وليس تصميماً مخصصاً — لأن هذا الجزء هو القلب الأمني للنظام، ومخاطرة إعادة التصميم من الصفر ليس لها ما يبررها
- يجب أن توثّق الدوال الحرجة أمنياً (منح/سحب Capability، إعادة تصنيف retype للذاكرة) شروطها المسبقة واللاحقة (pre/post condition) على شكل تعليقات منظّمة، حتى قبل دخول أداة إثبات صوري (مثل Kani أو Prusti) إلى المشروع — هذه التعليقات ستصبح لاحقاً الأساس المباشر لحواشي الإثبات (proof annotation)

## 2. نموذج Capability — القلب الأمني لكامل نظام التشغيل

بدلاً من نموذج UID/GID/permission التقليدي في لينكس، يُمثَّل كل مورد (ذاكرة، جهاز، منفذ IPC، رمز HAL-Direct) بواسطة **Capability**:

```rust
/// Capability واحد = مرجع غير قابل للتزوير إلى Kernel Object + مجموعة من الحقوق (rights)
pub struct Capability {
    pub object_ref: KernelObjectRef,
    pub rights: CapabilityRights,   // bitflags: READ, WRITE, EXECUTE, GRANT, DUPLICATE, REVOKE
    pub badge: u64,                 // معرّف اختياري لتمييز الطلبات أثناء الـ IPC
}

bitflags::bitflags! {
    pub struct CapabilityRights: u32 {
        const READ     = 0b00001;
        const WRITE    = 0b00010;
        const EXECUTE  = 0b00100;
        const GRANT    = 0b01000; // إذن بنقل هذا الـ Capability إلى عملية أخرى
        const DUPLICATE= 0b10000;
    }
}
```

**القواعد الأساسية:**
- لا تملك أي عملية بشكل افتراضي حق الوصول إلى أي مورد؛ فقط عند امتلاك Capability صالح
- تُنقل الـ Capabilities فقط عبر IPC صريح (`grant`)، وأبداً بشكل ضمني (implicit)
- يجب أن يكون السحب (Revocation) ممكناً: يجب أن تكون النواة قادرة على إبطال Capability واحد وكل مشتقاته (children في حالة duplicate) (نمط CDT — Capability Derivation Tree، مطابق لـ seL4)

## 3. إدارة الذاكرة (Memory Management)

لا تخصص النواة الصغرى صفحات بنفسها بمعنى `malloc` عام؛ بدلاً من ذلك **الذاكرة الفعلية نفسها هي Capability** (`UntypedMemory` — نموذج seL4 بالضبط):

- عند الإقلاع، تُسلَّم كامل الذاكرة الفعلية المُبلَّغ عنها في Hardware Manifest (من الطبقة ١) للعملية الأولى (Root Task في الطبقة ٣) على شكل عدة كائنات `UntypedMemory`
- Root Task هي المسؤولة عن توزيع هذه الذاكرة بين الخدمات، وليست النواة نفسها — أي أن **سياسة تخصيص الذاكرة ليست في النواة**، بل الآلية فقط
- العمليات الأساسية للنواة على الذاكرة هي: `retype` (تحويل UntypedMemory إلى نوع محدد مثل PageTable أو ThreadControlBlock أو Endpoint)، `map`، `unmap`

```rust
pub enum KernelObjectType {
    UntypedMemory,
    PageTable,
    ThreadControlBlock,
    Endpoint,        // للـ IPC
    Notification,    // للإشارات غير المتزامنة (async)
    CapabilitySpace, // جدول Capabilities الخاص بعملية ما
}
```

## 4. الجدولة (Scheduler)

هناك نمطان مدعومان من HAL (قسم Timer)، بما يتوافق مع احتياجات ملف تعريف (Profile) الطبقة ٤:

| النمط | الخوارزمية الأساسية | الاستخدام |
|---|---|---|
| Interactive | قائم على الأولوية (Priority) مع aging + كوانتوم زمني قصير (~1-4ms) | عام، ألعاب |
| Throughput/Batch | خوارزمية مخصصة (القسم ٤.١) | معالجة دفعية للذكاء الاصطناعي، احترافي |

### 4.1 القرار: خوارزمية مخصصة لنمط Throughput

بدلاً من تنفيذ CFS أو EEVDF مباشرة، تُصمَّم خوارزمية مخصصة من الأساس تكون مُحسَّنة لنموذجنا ثنائي النمط (dual-mode) (وليست خوارزمية عامة يتم ترقيعها لاحقاً). ملاحظات التصميم الأولية:

- **وحدة الجدولة ليست الـ thread فقط، بل «مجموعة IPC»**: لأنه في هذه الهندسة المعمارية، تكون العملية عادةً سلسلة IPC عبر عدة عمليات (مثلاً تطبيق ← VFS ← برنامج تشغيل)، يجب أن تأخذ الخوارزمية بعين الاعتبار تكلفة السلسلة كاملة، وليس فقط خيطاً (thread) منفرداً — وهذا ما لم تُصمَّم له لا CFS ولا EEVDF أصلاً (لأن هذه السلسلة غير موجودة إطلاقاً في نواة لينكس الأحادية الكتلة monolithic).
- **الوعي بـ NUMA وتقارب أجهزة الحوسبة (Compute Device Affinity)** كمُدخل من الدرجة الأولى للخوارزمية، وليس كطبقة جانبية تُضاف عليها لاحقاً (وهو أمر أُضيف لاحقاً وبصعوبة إلى EEVDF في لينكس أيضاً)
- **معيار اختيار الـ weight**: مزيج من الأولوية الثابتة (من Profile Policy) + مدة الانتظار في قائمة الانتظار (شبيه بـ aging) + معامل «تكلفة سلسلة IPC» المذكور أعلاه
- يجب إدارة مخاطر هذا المسار (التصميم من الصفر) عبر benchmark مكثف مقابل تنفيذ مرجعي شبيه بـ CFS على نفس عبء العمل (workload) — إذا لم تكن الخوارزمية المخصصة في الممارسة أفضل من CFS البسيطة، يجب العودة إلى نهج شبيه بـ CFS دون تعصب؛ يجب أن يبقى هذا القرار مبنياً على البيانات، لا أيديولوجياً

### 4.3 القرار النهائي: صيغة الـ Weight في نمط Throughput

**الصيغة الأساسية (النسخة الأولى؛ يتم ضبط معاملاتها الرقمية عبر benchmark حقيقي، لكن بنية الخوارزمية نفسها ثابتة):**

```
vruntime_next(thread) = vruntime_current(thread) + (actual_runtime_ns / effective_weight)

effective_weight = base_priority_weight
                  × (1 + aging_factor × min(wait_time_ms, aging_cap_ms))
                  × numa_locality_bonus
```

- **`base_priority_weight`**: يأتي من Profile Policy (الطبقة ٤)؛ مثلاً يمنح ملف تعريف الذكاء الاصطناعي (AI) قيمة أساسية أعلى لخيوط الاستدلال (inference)
- **`aging_factor` و`aging_cap_ms`**: للوقاية من التجويع (starvation)؛ كلما انتظر الخيط أطول في قائمة الانتظار ارتفع وزنه الفعلي، لكن هناك سقف حتى لا يفسد ترتيب الأولويات الأساسي
- **`numa_locality_bonus`**: الخيط الذي يُجدوَل على نواة (core) قريبة من ذاكرته/جهاز الحوسبة الخاص به يحصل على مكافأة (تخفيض في الزيادة التراكمية لـ vruntime)، لتشجيع المجدول على الحفاظ على القرب المكاني NUMA

**نموذج محاسبة سلسلة IPC:** بدلاً من محاسبة كل خيط في سلسلة IPC (مثلاً تطبيق ← VFS ← برنامج تشغيل) بشكل منفصل، تحصل كل الخيوط المشاركة في سلسلة IPC متزامنة واحدة على **Chain Group ID** مشترك، وتتراكم قيمة `vruntime` على مستوى المجموعة، لا على مستوى كل خيط بمفرده:

```rust
pub struct ChainGroup {
    pub id: ChainGroupId,
    pub member_threads: Vec<ThreadId>,
    pub group_vruntime: u64,
}
```

هذا يعني أن سلسلة IPC طويلة توزّع تكلفة جدولتها بإنصاف بين أعضائها، بدلاً من أن تحصل على ضعف أو ثلاثة أضعاف حصتها من المعالج لمجرد أنها أشركت عدة خيوط (وهي مشكلة موجودة في النماذج البسيطة مثل CFS الخام، لأن IPC لم يكن موجوداً إطلاقاً في تصميمه الأصلي).

**حسم المعاملات الرقمية:** القيم الأولية المقترحة لبدء الـ benchmark هي: `aging_factor = 0.02`، `aging_cap_ms = 50`، `numa_locality_bonus = 0.9` (تخفيض بنسبة ١٠٪ في الزيادة التراكمية لـ vruntime مقابل الوصول المحلي). هذه نقاط بداية، وليست أرقاماً نهائية — الضبط الدقيق جزء من مرحلة اختبار الأداء في الـ MVP، وليس سؤالاً معمارياً مفتوحاً.

### 4.4 ملاحظات عامة عن المجدول
- اختيار النمط يكون على مستوى **كل خيط (per-thread)** على حدة، وليس على مستوى النظام كله؛ يمكن لخيط استدلال ذكاء اصطناعي أن يكون في نمط throughput بينما تكون واجهة المستخدم على نفس الجهاز في نمط interactive
- يجب أن يكون المجدول على دراية بمعلومات طوبولوجيا NUMA (من HAL) لتقليل تكلفة الوصول للذاكرة عبر العُقد (cross-node)
- وراثة الأولوية (Priority Inheritance) إلزامية (للوقاية من انعكاس الأولوية priority inversion عبر سلاسل IPC)

## 5. IPC — قلب هندسة النواة الصغرى

بما أن كل شيء (برامج التشغيل، نظام الملفات، الشبكة) يعمل كعملية منفصلة في الطبقة ٣، فإن **أداء IPC يحدد مباشرة أداء النظام بأكمله**. هذا هو الجزء الأكثر أهمية للتحسين.

### 5.1 نوعان من الـ IPC

```rust
// ١. متزامن، رسالة صغيرة — للاستدعاءات السريعة الشبيهة بـ RPC على طراز syscall
pub struct Endpoint;
pub fn ipc_call(endpoint: Capability, msg: SmallMessage) -> SmallMessage;
// SmallMessage: بضع كلمات (word) كحد أقصى، تُنقل مباشرة في السجلات، دون نسخ ذاكرة

// ٢. غير متزامن، بيانات ضخمة — لنقل بيانات كبيرة الحجم (مثل مخزن AI/GPU)
pub struct Notification;
pub fn ipc_send_async(notif: Capability, shared_buffer: Capability);
```

### 5.2 Zero-Copy للبيانات الضخمة
بالنسبة للمخازن المؤقتة (buffers) الكبيرة (مثل إطار فيديو، أو tensor للذكاء الاصطناعي)، وبدلاً من النسخ، يتم نقل **Capability إلى منطقة ذاكرة مشتركة (Shared Memory Region)**؛ ويكتفي المستقبل بتعيينها (map) في فضاء عناوينه الخاص. عدد النسخ صفر.

```rust
pub fn create_shared_region(size: usize, rights: CapabilityRights) -> Capability;
pub fn map_shared_region(cap: Capability, at: Option<VirtAddr>) -> VirtAddr;
```

### 5.3 المسار السريع لـ IPC (Fast Path)
بالنسبة للـ Endpoints عالية حركة المرور (مثلاً بين المجدول وبرنامج تشغيل يعمل في الوقت الحقيقي)، يجب أن يكون هناك "fast path" يقلل تبديل السياق إلى أدنى حد — وهذا بالضبط هو التحسين الشهير في L4 الذي خفّض تكلفة IPC من نحو ميكروثانية إلى نحو مئات النانوثانية. يجب قياس هذا عبر benchmark وهو جزء من معايير القبول (القسم ٨).

## 6. نموذج Kernel Object

```rust
pub enum SyscallOp {
    Send { endpoint: CapId, msg: SmallMessage },
    Recv { endpoint: CapId },
    Call { endpoint: CapId, msg: SmallMessage },   // Send + Recv بشكل ذري (atomic)
    Yield,
    CapGrant { target_thread: CapId, cap: CapId, rights: CapabilityRights },
    CapRevoke { cap: CapId },
    Retype { untyped: CapId, target_type: KernelObjectType, count: usize },
    Map { page_table: CapId, frame: CapId, vaddr: VirtAddr, perms: MapPermissions },
}
```

يجب أن تبقى طبقة استدعاءات النظام **صغيرة جداً** (تملك seL4 نحو ١٠-١٥ استدعاء نظام؛ هدفنا مشابه، وليس قريباً من ٣٥٠-٤٠٠ استدعاء نظام في لينكس).

## 7. هيكل الدلائل

```
kernel/
 ├── kernel-core/        # موزّع استدعاءات النظام، object model، no_std، مستقل عن الهندسة المعمارية
 ├── kernel-mm/          # إدارة UntypedMemory، عمليات PageTable
 ├── kernel-sched/       # المجدول، نمطا Interactive + Throughput
 ├── kernel-ipc/         # Endpoint، Notification، Shared Region، fast path
 ├── kernel-cap/         # نموذج Capability، CDT، السحب (revocation)
 └── kernel-arch-glue/   # الجسر بين kernel-core وسمات (traits) hal-core (الطبقة ١)
```

## 8. معايير اكتمال الـ MVP
1. الإقلاع على الهندسات المعمارية الثلاث جميعها مع تسليم التحكم من HAL وإنشاء أول كائنات `UntypedMemory`
2. تنفيذ ناجح لـ Root Task حدّي (minimal) يُنشئ خيطاً ثانياً ويُقيم معه IPC متزامناً
3. Benchmark: تكلفة `ipc_call` على المسار السريع أقل من ٥٠٠ نانوثانية على العتاد المرجعي (هدف أولي؛ قابل للتعديل بعد benchmark حقيقي)
4. ذاكرة مشتركة zero-copy بين عمليتين مع إثبات (اختبار) أن لا نسخ بيانات قد حدث
5. اختبار السحب (Revocation): إبطال Capability وإثبات أن مشتقاته لم تعد صالحة أيضاً
6. اختبار fuzz لطبقة استدعاءات النظام (لأن هذه الطبقة هي سطح الهجوم الرئيسي للنظام)

## 9. الأسئلة المفتوحة المتبقية
لا توجد أي أسئلة معمارية مفتوحة متبقية في هذه الطبقة. الضبط الدقيق للثوابت الرقمية لصيغة الـ weight (القسم ٤.٣) هو بطبيعته جزء من مرحلة الـ benchmark في التنفيذ، وليس قراراً تصميمياً معلقاً.
