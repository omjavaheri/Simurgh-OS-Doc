# 西穆尔格 — 智能操作系统

> **一种围绕安全、隔离、硬件感知和智能计算构建的全新操作系统架构。**

## 为什么是西穆尔格？

每个操作系统都始于关于软件应如何与硬件交互的一系列假设。

几十年来，许多操作系统都遵循了一条相对相似的道路：一个大型的特权内核提供广泛的服务，而应用程序和系统组件则通过日益复杂的接口与该内核交互。

Linux 是这个模型多么成功的绝佳范例。它为从嵌入式设备和智能手机到云基础设施和超级计算机的一切提供动力。

但硬件正在改变。

现代系统不再仅仅是：

```text
CPU + 内存 + 存储 + 网络
```

一台当代计算机可能包含：

```text
CPU
├── 多个核心
├── 多个 NUMA 节点
├── GPU
├── NPU
├── TPU
├── FPGA
├── 高速存储
├── 高速网络
└── 多个异构内存域
```

与此同时，现代工作负载也变得越来越异构：

```text
交互式应用程序
游戏
云服务
AI 推理
AI 训练
实时工作负载
科学计算
边缘计算
```

这引出了一个简单的问题：

> **如果我们今天要设计一个操作系统，而不受现有操作系统历史演进的约束，它的基础会是什么样子？**

这个问题就是 **西穆尔格** 的出发点。

---

# 核心理念

**西穆尔格** 是一个从头开始围绕以下几个原则设计的实验性操作系统架构：

* 强隔离
* 基于能力的安全性
* 最小特权代码
* 硬件抽象
* 用户态系统服务
* 高性能 IPC
* 异构计算
* NUMA 感知
* 零拷贝数据交换
* 内存安全
* 以及为 AI 工作负载而设计的架构

这个名字来自 **西穆尔格**，一种与智慧、保护、知识和重生相关联的波斯神话之鸟。

名字背后的哲学是有意的：

> **西穆尔格 不打算成为另一个 Linux 发行版。它是对操作系统若为现代硬件和工作负载重新设计其基础，可能会是什么样子的探索。**

---

# 第一原则：保持特权核心小巧

西穆尔格 最重要的决策之一是采用 **微内核架构**。

西穆尔格 没有将驱动程序、文件系统、网络和其他操作系统服务放入一个庞大的特权内核内部，而是试图让特权内核只负责一组更小的基础机制。

概念上：

```text
┌───────────────────────────────────────────────┐
│                应用程序                        │
├───────────────────────────────────────────────┤
│              系统服务                          │
├───────────────────────────────────────────────┤
│      VFS / 网络 / 驱动程序 / 服务              │
│                 用户空间                       │
├───────────────────────────────────────────────┤
│                 微内核                         │
│                                               │
│   内存 • IPC • 能力 • 调度                    │
├───────────────────────────────────────────────┤
│                    HAL                        │
├───────────────────────────────────────────────┤
│                   硬件                         │
└───────────────────────────────────────────────┘
```

因此，架构的前两层是整个项目的基础：

**第 1 层 — 硬件抽象层**

**第 2 层 — 基于能力的微内核**

完整的架构有意从下往上开发。

---

# 01 — 硬件抽象层

操作系统必须回答的第一个问题是：

> **这台机器上实际存在什么硬件？**

西穆尔格 在硬件正上方放置了一个专用的 **硬件抽象层（HAL）**。

HAL 是唯一直接与硬件特定机制交互的层，例如：

* CPU 寄存器
* MMIO
* 中断控制器
* 架构特定指令
* 固件提供的内存映射
* 定时器
* 架构特定的启动机制

HAL 之上的所有层都应该看到一个抽象的硬件模型，而不是单个的 CPU 架构。

初始目标架构：

```text
x86_64
ARM64
RISC-V RV64GC
```

HAL 暴露通用的 Rust trait，这样微内核就不需要在其实现在各处包含架构特定的条件编译。

---

# 硬件发现而非硬件假设

西穆尔格 中一个特别重要的理念是 **发现 + 策略**。

HAL 不决定一台机器是：

```text
游戏
AI
专业
通用
```

它只是发现机器实际包含什么。

例如：

```text
CPU
64 核心

内存
256 GB

GPU
NVIDIA ...

NPU
可用

NUMA
4 个节点

IOMMU
可用
```

这些信息被转换为标准化的 **硬件清单**。

因此，上层不需要知道机器是通过 UEFI、设备树还是其他架构特定机制启动的。

当前的设计也将 GPU/NPU/TPU/FPGA 资源视为一等计算资源，而不仅仅是通用的外设。

---

# 02 — 微内核

第二个基础是 西穆尔格 微内核。

微内核有意只包含一小组基础机制：

```text
内存管理
能力管理
IPC
调度
线程
内核对象
```

目标不是在内核内部构建一个更小版本的 Linux。

目标是让系统的特权部分 **小巧、可理解、可审计且强隔离**。

微内核通过受控的系统调用边界与用户态服务通信。

---

# 基于能力的安全性

这也许是架构上最根本的区别。

传统的 Unix/Linux 安全性严重围绕以下概念：

```text
UID
GID
文件权限
ACL
Root
```

西穆尔格 转而使用 **能力作为基本的授权原语**。

一个进程不会仅仅因为以某个特定用户身份运行就自动获得对资源的访问权。

它需要一个授予对该资源访问权的能力。

概念上：

```text
进程
   │
   ├── 能力 → 内存
   │
   ├── 能力 → 设备
   │
   ├── 能力 → IPC 端点
   │
   └── 能力 → 共享内存
```

一个能力包含对一个内核对象的引用以及明确的权限。

能力也可以被明确地转移和撤销，包括通过能力派生模型派生的能力。

这给 西穆尔格 提供了一个安全模型，其中：

> **访问是进程明确拥有的东西，而不是它从身份中隐式继承的东西。**

---

# 为什么这很重要

考虑一个设备驱动程序。

在传统的宏内核架构中，驱动程序通常在特权内核空间中执行。

如果驱动程序包含严重错误，后果可能会波及内核本身。

西穆尔格 则旨在将驱动程序作为隔离的用户态进程运行。

概念上：

```text
┌────────────────────────────┐
│        设备管理器           │
├────────────────────────────┤
│        驱动程序进程          │
│                            │
│  能力：                    │
│    MMIO → 设备 A          │
│    IRQ  → 设备 A          │
└────────────────────────────┘
```

一个驱动程序应该只接收其特定设备所需的能力。

因此，架构目标是：

```text
驱动程序崩溃
     ↓
重启驱动程序
     ↓
系统继续运行
```

而不是：

```text
驱动程序崩溃
     ↓
内核损坏
     ↓
系统崩溃
```

这种用户态隔离模型是微内核架构的核心动机之一。

---

# IPC 是性能关键部分

微内核架构引入了一个重要挑战：

> **隔离组件之间的通信必须极其高效。**

因此，在西穆尔格 中，IPC 被视为一等架构组件，而不是实现细节。

提出了两条主要通信路径：

### 小型同步消息

对于只传输几个字的操作：

```text
进程 A
   │
   │ IPC 调用
   ↓
进程 B
```

消息可以在不复制大缓冲区的情况下传输。

### 大数据

对于诸如此类的内容：

```text
AI 张量
GPU 缓冲区
视频帧
网络数据包
```

西穆尔格 使用共享内存能力。

代替：

```text
进程 A
 ↓ 复制
内核
 ↓ 复制
进程 B
```

架构目标是：

```text
进程 A
      │
      ▼
共享内存
      ▲
      │
进程 B
```

实现零数据拷贝。

这明确是微内核设计的一部分。

因此，MVP 包含对 IPC 快速路径进行基准测试的目标，而不是简单地假设架构会很快。

# 不同的调度方法

现代工作负载并不相同。

桌面 UI 想要：

```text
低延迟
```

AI 推理引擎可能想要：

```text
最大吞吐量
```

游戏可能关心：

```text
帧时间一致性
低输入延迟
GPU 局部性
```

服务器可能关心：

```text
吞吐量
NUMA 局部性
可预测性
```

因此，西穆尔格 将调度行为划分为如下模式：

```text
交互式
吞吐量
```

并将 NUMA 和计算设备局部性作为调度决策的显式输入。

提议的设计还引入了 **IPC 链组** 的概念，允许诸如：

```text
应用程序
    ↓
VFS
    ↓
驱动程序
```

这样的链被视为一个连接的调度工作负载，而不是不相关的线程。

重要的是，这是 西穆尔格 打算 **以基准为导向** 的领域。如果自定义调度器在参考工作负载上无法胜过经过验证的类 CFS 调度器，那么设计应该被重新考虑，而不是因为意识形态原因而被辩护。

# 为什么选择 Rust？

选择 Rust 主要不是因为潮流。

它直接源于架构。

操作系统包含一些最危险的软件错误类别：

```text
缓冲区溢出
释放后使用
双重释放
数据竞争
无效内存访问
并发错误
```

这些错误在特权软件中尤其危险。

Rust 为 西穆尔格 提供了对此类项目有吸引力的组合：

```text
底层控制
+
内存安全
+
强类型系统
+
并发保证
+
无垃圾回收器
```

这尤其有价值，因为 西穆尔格 打算将尽可能多的功能移出特权内核。

因此，架构在整个 HAL 和微内核中使用 Rust，在最底层使用 `no_std`，并且仅在早期启动期间需要的地方使用最少的架构特定汇编。

理念很简单：

> **在硬件需要的地方使用不安全代码，但让每个不安全边界都是明确、最小且有文档的。**

---

# 西穆尔格 vs. Linux

西穆尔格 的目的 **不是** 声称 Linux 已经过时。

Linux 是有史以来最成功和最重要的操作系统之一。

问题不同：

> **如果我们今天从一个干净的架构基础开始，我们会做出什么样的权衡？**

以下是高层次的区分：

| 领域 | Linux 方法 | 西穆尔格 方向 |
| -------------------- | ------------------------------------ | ------------------------------------------ |
| 内核架构 | 大型宏内核 | 微内核 |
| 驱动程序 | 主要在核心态 | 用户态隔离 |
| 安全基础 | UID/GID + 权限 + 能力 | 能力优先 |
| 硬件抽象 | 架构特定的内核代码 | 专用 HAL |
| IPC | 多种机制 | 一等内核原语 |
| 大数据传输 | 多条路径 | 基于能力的共享内存 |
| 故障隔离 | 对内核组件有限 | 进程级隔离 |
| 内存安全 | C + 其他语言 | Rust 优先 |
| CPU 架构 | 广泛支持 | 上层架构中立 |
| NUMA | 受支持 | 设计为调度的一等输入 |
| AI 加速器 | 不断发展的生态系统 | 一等发现模型 |
| 内核大小 | 非常大 | 有意最小化 |
| 系统服务 | 许多内核集成组件 | 用户态服务 |

重点是 **这些是架构目标，而不是已证实的优越性声明**。

西穆尔格 必须通过实现和基准测试来赢得每一项性能和可靠性声明。

# 西穆尔格 在哪些方面可能有优势？

## 1. 安全性

较小的特权内核意味着在最髙特权级别运行的代码量更少。

结合能力：

```text
最小内核
+
能力安全
+
进程隔离
+
Rust
```

该架构旨在减少组件故障的后果。

---

## 2. 故障隔离

驱动程序不应仅仅因为控制硬件就成为可信计算基础的一部分。

相反：

```text
驱动程序
 ↓
能力
 ↓
设备
```

这创造了独立重启各个组件的可能性。

---

## 3. 硬件演进

HAL 有意将硬件发现与操作系统策略分离。

这意味着未来的硬件，如：

```text
GPU
NPU
TPU
FPGA
CXL 内存
```

可以在硬件清单中表示，而不需要整个上层架构去理解每个硬件供应商的实现。

---

## 4. AI 工作负载

AI 工作负载与传统桌面工作负载有根本不同。

它们高度依赖：

```text
GPU/NPU
内存带宽
NUMA 局部性
大型共享缓冲区
DMA
高速网络
```

西穆尔格 的架构从一开始就考虑这些资源，而不是将 AI 视为后来添加的应用程序类别。

以下组合：

```text
异构计算发现
+
NUMA 感知调度
+
基于能力的设备访问
+
零拷贝共享内存
+
高性能 IPC
```

旨在为面向 AI 的系统服务提供基础。

# 但 西穆尔格 有实际成本

一个严肃的开源项目也应该诚实地对待其缺点。

微内核架构并不自动更快。

它引入了：

```text
IPC 开销
上下文切换
更复杂的服务协调
更复杂的调试
更多组件
更多接口
```

一个新的文件系统很难。

一个新的驱动程序生态系统很难。

POSIX 兼容性很难。

支持多个 CPU 架构很难。

而建立一个可与 Linux 相媲美的生态系统是一项巨大的工程。

因此：

> **西穆尔格 首先是一个架构实验，只有当实现证明了架构在实践中有效时，它才是一个生产级操作系统。**

这个区分很重要。

# 目标

西穆尔格 的目标不是用不同的源代码重新创建 Linux。

它是探索一组不同的基本假设：

```text
硬件是异构的。
安全性应该是基于能力的。
驱动程序不应该需要内核特权。
特权核心应该最小化。
通信应该明确且快速。
大数据应该在没有不必要拷贝的情况下移动。
调度应该理解现代硬件拓扑。
内存安全应该是一个基础属性。
AI 应该被视为一等工作负载。
```

最重要的是：

> **架构应该由测量来判断，而不是由意识形态。**

如果一个想法更快、更安全或更可靠，我们就保留它。

如果基准测试证明传统方法更好，我们就采用更好的方法。

这就是 **西穆尔格** 的精神。
